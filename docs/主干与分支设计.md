# 循证 Trace：主干与分支设计审阅

审阅日期：2026 年 10 月 24 日。本文依据当前仓库的类型、调查逻辑、页面操作与测试，区分已经实现的能力和建议方案。本文只涉及产品与代码设计，没有调用真实搜索、模型接口，也没有重新核验演示资料的外部正文。

## 1. 先确定分支究竟表示什么

主干围绕一个根问题，记录调查者愿意纳入当前报告的调查过程、判断依据、适用条件和未解问题。“纳入”表示调查者选择讨论这条记录，不表示这条记录或其中的说法已经被判定为真。主干可以同时保留支持、反对和无法判断的资料。

分支表示从某一节点展开的子问题、替代解释或反证方向。例如“这张照片的拍摄条件是什么”“有没有足以推翻当前判断的材料”。分支名称应当描述要查清的问题，不能把“官方”“小红书”“B 站”等平台名当成分支的核心含义。一个问题可以使用多个来源，同一个来源也可以服务多个问题。

来源筛选回答“去哪里查”；分支回答“沿哪个问题继续查”；证据关系回答“这份材料针对哪个主张，起什么作用”。三者应当分别建模。

分支从选中的历史节点开始，应继承分叉节点及其之前的有效上下文，而不继承主干后来才发现的资料。这里的完整上下文包括问题定义、计划、资料引用、针对主张的标注与当时的判断；当前版本只对提交与证据可达性实现了这一点，尚未对完整调查状态实现快照。

合并表示“把这条调查方向的哪些结果纳入主干，并保留来路”，不能表示“分支得到了系统认证”。合并之后可以继续存在相互冲突的证据；后续出现新材料，可以在原分支继续提交，或者从旧节点再开一个问题分支。

## 2. 当前代码确实实现了什么

| 能力 | 当前实现 | 准确的参赛表述 |
| --- | --- | --- |
| 提交历史 | `Commit.parents` 是数组，提交保存分支标识、时间、资料引用和可选检索信息；`appendCommit` 推进目标分支末端 | 每次收录与检索形成可追溯节点 |
| 从历史分叉 | `app/page.tsx` 的 `createBranch` 使用 `selected.id` 作为新分支的 `head` | 可以从选中的历史节点展开新调查方向 |
| 提交隔离 | `branchCommits` 从分支 `head` 沿所有父节点回溯；`branchEvidence` 只返回可达提交引用的资料 | 未合并旁支的新增资料不会自动出现在主干资料列表 |
| 搜索落点 | `collectClues` 固定本轮目标 `branchId`；`applySearchResult` 将结果提交到该分支，并保留用户当前查看的分支 | 检索结果会保存到发起调查时指定的分支 |
| 来源与分支分开 | `Investigation.sources`、`PlanStep.sources` 与 `Branch` 分离；来源选择器与分支选择器分别存在 | 可以选择公开来源范围，并从问题节点展开不同调查方向 |
| 全局资料去重 | 自动收集通过 `safeUrl` 规范化 HTTP/HTTPS URL，同一档案内复用已有资料 ID | 同一档案内，相同规范化 URL 的自动检索结果只保存一份资料 |
| 双父合并 | `mergeBranch` 把主干末端与来源分支末端交给 `appendCommit`；原分支保留 | 合并保留两条调查历史与来源分支，且不会自动裁定真伪 |
| 报告边界 | 报告说明人工关系标签不等于最终裁定；无可达资料时明确证据不足；演示档案有标识 | 报告包含原文链接、人工关系标签、版本记录和未解提醒 |

需要补充两处细节：

1. URL 去重是同一份 `Investigation` 内的去重，并不是跨全部调查档案的共享文献库；也不是对所有追踪参数、镜像页面、转载或内容相似度的语义去重。来源独立性仍需人工判断。
2. 自动检索遇到其它分支已经保存的 URL，会复用资料 ID，并在当前分支的新提交中引用它；手工添加在遇到重复 URL 时直接提示“已收录”，尚没有“复用并引用到当前分支”的入口。因此不能声称所有路径都支持跨分支复用操作。

当前图谱展示的是整个档案的提交图，切换分支会影响可达记录、证据列表和报告，并不意味着图谱会隐藏其余所有分支。选中某个历史节点，也不等于把页面的全部调查状态回退到了那个时刻。

## 3. 三个最重要的不足与最小修复

### 3.1 证据关系保存在全局资料上，分支标注会相互影响

**代码依据：** `lib/types.ts` 把 `relation` 放在 `Evidence` 上；`app/page.tsx` 的 `changeRelation` 直接修改 `Investigation.evidence` 中的对象，没有创建提交。`applySearchResult` 复用已有 URL 时也保留这份全局标注。

**影响：** 同一份 ESA 材料可以支持“存在近地轨道摄影记录”这个子主张，同时只为“月球肉眼可见”提供背景。当前只能保存一个关系值。在旁支把它改为“支持主张”，主干及其它引用它的分支也会显示这个关系；历史报告读取的也是现值，不能回看当时的标注。当前没有独立的 `Claim` 类型，界面里的“主张”对象也没有明确的主张 ID。

**建议的最小正确修复：** 继续让资料库按 URL 保存一份客观来源，把“资料—主张”的关系变成提交中的不可变标注事件。事件至少记录资料 ID、目标问题或主张 ID、关系、理由；标注操作创建一个新提交。根据所选节点回放该方向的标注，分叉自然继承分叉点之前的记录。合并时仅纳入显式选择的标注，避免另一个父节点的标签无条件覆盖主干。

可以先用分支的问题字段作为目标问题，随后再引入完整的主张实体。不要仅添加一个当前分支的关系映射，就宣称历史节点的标注也可以准确回溯：映射如果被原地覆盖，仍然没有历史快照。

**必须覆盖的测试：** 同 URL 在两个问题下可有不同关系；旁支改标记不改变主干；从旧节点分叉只能继承当时的标记；合并不因遍历顺序覆盖主干标记；导出、导入后仍保留上述行为。类型修改要同步 `lib/validation.ts`，因为当前校验器会剥离未知字段。

**参赛前建议：** 如要演示“同一资料在不同问题中承担不同作用”，应优先修复并完成上述验证。时间不足时，明确说明“当前关系标签在同一档案内共享，分支主要隔离调查历史与资料引用”，演示中不要把相互独立的分支标注当成已实现能力。

### 3.2 合并把历史可达资料全部带入报告，尚不能挑选采纳内容

**代码依据：** `mergeBranch` 的 `evidenceIds` 收录当前分支全部可达资料。更关键的是，`branchEvidence` 会遍历所有父节点，因此即使把合并节点的 `evidenceIds` 改为空，第二父节点历史中的资料仍会进入主干集合。`tests/investigation.test.mjs` 的“双父合并保留两条历史”用例正好验证了这种行为。

**影响：** 当前合并保留来源的目标已经实现，但“完整历史”“主干选择引用的资料”“主干接受的结论”没有区别。报告会列出合并旁支中的全部可达资料。界面虽然明确不自动裁定真伪，仍不能表达只采纳某条条件说明、暂缓某条截图、保留一项冲突、拒绝某个推断。支持/反驳数量也只是标签计数，不是来源独立性、证据强度或共识度。

**建议的最小正确修复：** 保留双父的历史图，新增合并记录，至少包含：

- 选入主干报告的资料 ID 及针对的主张。
- 纳入的结论与适用条件，由调查者填写或确认。
- 暂不采纳的资料或推断及理由。
- 已发现的冲突、仍未解决的问题和下一步。

历史浏览继续使用全部父节点的可达性；主干报告单独计算采纳集合：沿第一父节点继承主干原有选择，再应用本次显式纳入、暂缓与排除决定。第二父节点用于追溯，不自动把其所有资料视作采纳。后续还要允许撤销或更新早先的采纳决定，并留下新提交。

不要通过删除第二父节点实现资料挑选，这会丢失来源历史；也不要只改合并节点的 `evidenceIds`，现有回溯算法下不会解决问题。合并记录写入 `description` 可以作为短期人工说明，但如果报告仍列出全部祖先资料，就不能称为已支持“选择性合并”。

**必须覆盖的测试：** 合并具有双父且保留原分支；未选资料仍能在历史中追溯，但不列入已采纳资料；相反证据可同时被纳入；重复来源不重复计数；冲突和未解事项可导出；后续可撤销早先的采纳决定。

**参赛前建议：** 必须在文案中把当前操作说明为“汇合调查历史与资料，不等于采纳全部结论”。可以先加合并范围预览和人工摘要，这是较小的界面改动，但应如实标注仍为全量历史汇合。真正的选择性采纳需要报告逻辑、校验器和测试同步，完成之前应列入路线图。

### 3.3 分支没有自己的问题与计划快照

**代码依据：** `Branch` 当前仅有 `id/name/head/color`。`Investigation.steps` 与 `Investigation.sources` 是全局状态。编辑查询词直接改 `active.steps`；`setCaseSources` 会调整全局范围与未完成步骤；搜索执行状态也写回同一份 `steps`。`pendingSteps` 已通过分支可达的搜索提交区分“本方向是否查过某个查询”，这是部分隔离，并不是完整计划隔离。提交保留了实际执行的查询词，但没有持久化完整的来源选择快照。

**影响：** 从旧节点开分支，资料和提交不会看到主干未来的证据，但看到的仍可能是后来改过的全局计划；在旁支编辑查询词也会改变主干展示的计划。页面显示的完成数量基于全局 `steps.status`，可能与当前分支真正可达的检索记录不一致。报告的步骤也使用全局现值。

**建议的最小修复分两层：**

1. 先给分支补充明确的问题、方向类型（子问题/替代解释/反证）和分叉节点；把实际执行的查询词、来源范围和目标问题保存在搜索提交中。计划进度依据当前分支可达记录展示。历史节点详情明确只展示已保存的记录，不假装恢复完整状态。
2. 若要兑现“继承分叉前完整上下文”，再把计划变更与问题定义也版本化：在计划提交中保存快照或不可变变更，创建分支时从选中节点还原；不能直接复制分叉时页面里最新的 `active.steps`。分支创建后，各自的计划变更应独立推进。

只给分支复制一份当前 `steps`，可以提供“新建之后计划独立”，但不能恢复“从历史节点继承当时计划”。这两个能力应分开验收。

**必须覆盖的测试：** 主干后来的查询编辑不影响从旧节点创建的分支；旁支编辑不改变主干；同查询不同来源的真实执行记录可区分；各分支的完成数量与可达执行记录一致；刷新和导入后计划语义不变。

**参赛前建议：** 先补问题说明、执行记录与准确的进度提示；完整计划快照属于较大数据模型调整，建议在比赛版本稳定后推进。参赛资料使用“继承分叉前的提交与资料引用”，不要写“冻结全部调查上下文”。

## 4. 长城案例：主干、摄影分支与反证分支

以下是产品模型示例。资料名称与内容取自仓库的预置演示摘要，用于说明关系与流程；本文没有重新核读 NASA、ESA 的外部原文，不能把本段当作新的事实核验报告。

### 4.1 主干保留根问题与判断边界

根问题 Q0：“长城是唯一能从月球上肉眼看见的人造建筑，这是真的吗？太空照片能证明吗？”

主干先提交 C0“收录原始说法”，再提交 C1“拆分核验条件”：观察地点是否真的是月球、观察是否依赖镜头、可见对象是否确实为长城、“唯一”的范围是什么。主干到 C2 时可以继续查原始传播语境，并保留“尚未形成最终判断”。来源范围可以选择官方与机构、媒体或公开网页，它们都是查询条件。

从 C1 分别开两个问题分支，而不是分别创建“NASA 分支”“B 站分支”：

| 分支 | 具体问题 | 要核查的内容 | 可使用的来源 |
| --- | --- | --- | --- |
| 近地轨道摄影 | 已传播的太空照片究竟证明了什么？ | 原始图片、拍摄位置、器材、对象、裁切与原说明 | 航天机构原文、媒体转述、公开视频等 |
| 主动寻找反证 | 有没有直接否定 Q0 或限制其条件的一手说明？ | 对“月球”“肉眼”的直接回应，同时主动寻找可能推翻当前否定判断的新材料 | 航天机构、研究机构、公开原始记录等 |

两个分支都继承 C1 之前的根问题与已有资料，不自动继承主干后来 C2 取得的资料。以当前代码实现而言，提交与资料引用满足这个规则，计划与标注仍有前述限制。

### 4.2 摄影分支：一份资料可以服务不同主张

P1：收录演示中的 ESA 问答资料 E1，检查原始描述是否能支持子主张 Q1“存在近地轨道中的观察或摄影经历”。P2：收录演示中的观察距离背景 E2，解释为什么需要区分不同观察位置。若另有转发截图 E3，但找不到原始图片说明，就把它记作“出处待核”，不能从截图直接跳到 Q0 成立。

在建议模型中，E1 与 Q1 的关系可以是“支持，限于原文实际条件”；E1 与 Q0 的关系是“补充背景，不能跨越观察地点和观察方式推论”。资料库仍只保存一份 E1，关系绑定到具体问题与提交。

当前版本的 `Evidence.relation` 只能存一个标签，因此演示时应继续使用“补充背景”，并在摘录中写明它讨论的条件，不能现场宣称已经实现同资料的多主张独立标注。

### 4.3 反证分支：检验根主张，也检验当前判断

R1：寻找直接回应月球肉眼可见性的资料，收录演示中的 NASA 原始说明 E4。若核读正文与摘要一致，则将它对 Q0 标为“反驳”，记录它针对的确切条件。R2：继续寻找独立的原始说明或足以支持相反结论的记录；没有找到有效材料，也保留查询与空结果，不把“没搜到”当成“绝对不存在”。

该分支还应主动问：“是否存在可信的原始观察记录，能推翻我们现在倾向的判断？”反证不应成为只收集某一方向材料的筛选器。对于无法确认拍摄地点或观测方式的正面说法，可以保留冲突与待查状态。

### 4.4 合并时写清采纳范围

建议先从摄影分支形成 M1：保留主干 C2 与摄影分支 P2 两个父节点；纳入 E1、E2 所支持的条件说明，暂缓 E3，明确“近地轨道摄影信息不能直接推出月球肉眼可见”。这不是把摄影分支里所有资料投票为同一结论。

再从反证分支形成 M2：保留 M1 与 R2 两个父节点；纳入 E4 及人工核读说明，同时保留相反材料的存在、出处问题与尚未核验的细节。主干可以给出有条件的当前判断，也可以维持“证据不足”；该文字必须由调查者根据原文确认，不能由合并按钮自动生成事实裁定。

建议模型的历史形状如下：

```text
主干：C0 → C1 → C2 → M1 → M2
摄影：     C1 → P1 → P2 → M1
反证：     C1 → R1 → R2 → M2
```

三行中重复出现的 C1、M1、M2 分别代表同一个节点。精确父节点为：`P1.parents=[C1]`、`R1.parents=[C1]`、`M1.parents=[C2,P2]`、`M2.parents=[M1,R2]`。

建议的 M2 合并记录示例：

- 纳入的资料：E1、E2 的观察条件说明，以及 E4 对根问题的直接回应；每条保留原文链接与人工核读理由。
- 当前判断：依据已核读的有效资料，分别陈述月球、近地轨道、肉眼和镜头条件；不把“太空照片”当成所有条件通用的证明。
- 暂不采纳：E3 尚无可核对的原始出处，不能用作肯定根主张的依据。
- 保留的冲突：不同说法使用的“太空”“看见”含义不一致；存在相反转述时继续保留并标记适用条件。
- 未解问题：“唯一”是否有明确范围、特定照片的完整说明、历史观察记录的原始语境。
- 下一步：优先核读原始材料、核对图片与具体观察条件，再决定是否修订当前判断。

现有版本只能通过双父合并把整个可达资料历史汇合到主干，尚不能执行这里的资料挑选与结构化决定。仓库 `createDemo` 也只有一个“核验观察条件”旁支，尚未预置第二个反证分支；上述三方向流程是建议方案，不能冒充当前示例的既有界面。

### 4.5 新资料出现后可以继续调查

如果后续出现一份声称能够支持 Q0 的原始观察记录，原摄影、反证分支不应被删掉。可以在 R2 后追加 R3 检查它的地点、方式和出处；也可从 M2 新建“复核新观察记录”分支。已有矛盾继续保留，直到有证据解释或调查者给出明确理由。

当前实现没有“关闭/重开”状态机，但合并后原分支仍存在，可以切换回原分支继续提交，或从旧节点再开新分支。应使用这个准确表述，不宣称已经实现完整的分支审批生命周期。

## 5. 参赛材料应如何写

可使用的核心表述：

> 循证 Trace 把调查过程组织成可回溯的提交图：围绕根问题保存调查记录，从历史节点展开不同核验方向，按公开来源范围搜索资料，并在合并时保留两条历史。证据关系是人工标记，合并不会自动裁定主张真伪。

若未进一步改代码，应明确标记的边界：

- 当前分支隔离的是提交与资料可达性；计划及关系标注仍有共享字段。
- 当前合并汇合可达历史和资料，尚未实现逐项采纳、冲突处理与结构化结论。
- 当前报告提供来源与过程，不计算事实真值、可信度分数或多方共识；条数不等于证据权重。
- 支持接入与真实检索的能力，应以实际完成的验证记录为准，预置演示资料不能算成真实 API 查询。

推荐比赛前优先完成准确说明、合并范围提示和有针对性的演示；只有数据模型、备份校验和对应测试都完成后，才把分支独立标注或选择性合并升级为“已实现”。完整计划快照与多主张实体可作为下一阶段设计。
