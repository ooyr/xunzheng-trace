# 循证 Trace · 演示与提交脚本

> 像 Git 一样调查，让结论有迹可循。

本文为 2026 年参赛时准备的录制与提交模板，不是当前功能清单。以下三次查询尚未在本文件登记实际结果；空白字段不构成完成情况证明。已保存的接口联调范围见 [接入验证记录](接入验证.md)。只有真实调用、核对原文后才能填写结果，演示模式数据不能作为参赛要求中的真实查询。

## 开录前

1. 接通实际元宝搜索端点与认证，确认页面状态显示真实搜索可用。按需配置支持图片的模型。
2. 用公开问题完成一次试跑，检查错误提示、真实返回以及来源链接。
3. 清理或另建演示案件，使旧示例与本次真实查询能够区分。
4. 录制时隐藏 API 密钥和账户信息。已有截图先自行检查是否含个人信息。
5. 确认作品链接能被评委访问；如果有登录限制，提供可用体验方式。

## 三次真实查询

建议每次独立录一段短演示，保留完整结果与可点击来源。可以按检索质量调整题目，但不要用预设答案覆盖真实返回。

## 三分钟主展示

### 0:00—0:20 · 介绍问题

画面：工作台首页。

旁白：“搜索得到一个答案，并不代表知道它为什么可信。循证 Trace 把问题拆成线索，把证据和不同假设保存下来，像 Git 一样调查，让结论有迹可循。”

### 0:20—0:45 · 输入与拆解

画面：输入其中一个已经真实验证过的案例，展示生成的调查步骤，修改一个步骤。

旁白：“输入文字、链接，或者上传已有截图。AI 先拆出可核验的主张，我们可以修改计划，再选择要查的来源。”

若截图识别尚未接通，使用文字或链接演示，并删去关于自动识图的旁白。

### 0:45—1:20 · 元宝搜索与原始证据

画面：执行一个步骤，展示真实搜索结果，点开一条原始来源。

旁白：“这里由元宝搜索执行检索。每条证据都保留标题、原始链接和查询时间，用户可以自己打开确认。如果没有查到足够证据，就保留未知。”

真实网络等待较长时可剪辑等待过程，但应保留输入、运行状态与实际结果，避免让样例看起来像实时调用。

### 1:20—1:55 · 分支与修正

画面：从某条线索建立另一个调查分支，补充证据，比较两个解释。

旁白：“一种解释不够时，可以建立另一条分支。新的证据可以支持原来的解释，也可以让我们修正它。过程保留下来，结论就有迹可循。”

仅展示当前版本真正支持的分支行为；若尚无版本比较功能，不使用“自动回滚”“自动合并冲突”等描述。

### 1:55—2:25 · 报告与来源

画面：调查结论和 Markdown 导出。

旁白：“报告同时交代结论、依据和待确认的问题。导出后，别人仍能通过原始链接检查证据。”

### 2:25—2:45 · 三次真实查询

画面：展示三份已填写的真实查询记录或已录制结果。

旁白：“我们用规则查证、技术说法核验和科学知识核验测试了这条流程。这里是三次真实查询的记录与来源。”

只有三次都已执行并保存材料时才能使用这句旁白；未完成就据实说明当前进展。

### 2:45—3:00 · 当时规划与收尾

画面：工作台及机器人入口。

旁白：“下一步用微信公众号或企业微信，把同一套调查做成文字游戏式操作，再增加用户主动订阅的持续查证。”

此为历史旁白。当前已实现后台复查入口，正式录制时请按 [项目首页](../README.md) 与 [后台盯梢调度](后台盯梢调度.md) 更新措辞；微信正式调查入口仍待接通。

如果尚未接入微信，明确写“机器人演练 / 待接入微信”，避免让评委误以为已能在微信直接使用。
